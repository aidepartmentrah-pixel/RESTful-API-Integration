# v1.1 vendor spec vs. prior contract vs. mock vs. real-server evidence

**Date:** 2026-09-08
**Trigger:** the vendor sent a new, more detailed OpenAPI spec (v1.1),
saved as `Hospital_Directory_API_OpenAPI_v1.1.yaml`. This document compares
it against everything else already known about this API, and records the
decision made about how to proceed.

## Executive summary

1. **v1.1 describes a different patient-search interface than anything we
   had directly tested.** The prior contract (`Hospital_Directory_API_OpenAPI.yaml`
   v1.0.0) used one free-text `q` parameter. Direct real-server evidence
   gathered before v1.1 arrived (`real-evidence/`) also only ever tested a
   single free-text `q` string, and found it needs at least 3 words
   (first+father+last) or it's rejected. **v1.1 replaces this with three
   separate structured parameters** — `first_name`, `father_name`,
   `last_name` — each matched against its own column. Nobody has tested
   whether the real server actually accepts that structured shape; only the
   single-string shape has been directly confirmed.
2. **Decision made (2026-09-08): adopt v1.1 fully in the mock now**,
   including the unverified structured-search shape. Rationale: v1.1 is the
   vendor's formal written contract, and the mock/HCAT should be built
   against what the vendor is contractually obligated to deliver — not
   pre-emptively worked around based on a guess about what production
   currently does. If the real server doesn't honor this shape, that is a
   vendor bug to raise, not a design constraint to inherit.
3. **The evidence used to justify the *previous* mock change (single-`q`,
   3-word gate) is weaker than its own README claims.** Reading
   `real-evidence/2026-08-25_muslim-arabic-toolkit-run/report.json`
   directly: of 49 logged checks, only 2 are tagged `CONFIRMED_REAL`. Most
   others are tagged `MOCK_ONLY` or `SPEC_UNVERIFIED` by the toolkit's own
   classification, several have a blank `Path`, and one row hits
   `/patients/P-90001` — a mock-only fixture id that cannot exist on the
   real server. This strongly suggests that run mostly exercised the mock,
   not the real server, despite the folder name and the confident tone of
   its README. The `2026-08-17_first-real-server-capture/raw-http-capture.txt`
   file remains the highest-confidence evidence (a verbatim transcript with
   concrete dotted-numeric IDs and real response bodies) and should be
   weighted over the 08-25 run wherever they'd conflict.
4. **v1.1 independently resolves one confirmed real bug.** Real evidence
   showed `/workers?q=...` on the real server returns the same total
   regardless of `q` — silently ignored. v1.1 removes `q` (and
   `active_only`) from `/workers` entirely. That isn't a coincidence: it
   means `/workers` was never meant to support search server-side, and the
   mock's prior behavior of *actually filtering* on `q` there was itself
   the divergence.

## Resource-by-resource comparison

Confidence key: **CONFIRMED_REAL** = `2026-08-17_first-real-server-capture/raw-http-capture.txt`,
a verbatim transcript against the real server. **WEAK** =
`2026-08-25_muslim-arabic-toolkit-run`, whose own `report.json` tags most of
its rows `MOCK_ONLY`/`SPEC_UNVERIFIED` rather than `CONFIRMED_REAL` — treat
as suggestive, not proven. **UNTESTED** = asserted by a document, never
checked against the real server by any evidence file in this repo.

| Min. name requirement | 3 fields required together (b) | ≥3 whitespace-separated words in `q` | ≥3 words in `q` rejected with a specific message (WEAK — only 2 of 7 word-count rows tagged CONFIRMED_REAL) | Same underlying rule, different mechanism (structured fields vs. word count) |
| `patient_id` format | Plain numeric string, no `P-` prefix, no trailing `.0` | `P-10025` style | Dotted-numeric, e.g. `5690.47148`, `8528.69` (CONFIRMED_REAL) | v1.1 and real evidence agree on "no P- prefix"; neither the mock's old prefix nor v1.1's "plain numeric" description matches the real dotted-decimal format exactly. ## Known real-server deviations from the v1.1 contract (raise with the vendor, don't design around)

These are things the real server currently does that violate what v1.1
itself promises. They are **not** implemented in the mock, because the mock
represents the contract the vendor is supposed to deliver:

- **Mojibake Arabic text** in every response field (UTF-8 bytes read back as
  Latin-1) — v1.1 implies correct encoding is expected.
- **`patient_id`/`doctor_id`/`employee_id` are dotted-numeric** (e.g.
  `5690.47148`), not the "plain numeric" shape v1.1 describes.
- **`POST` to any endpoint returns `500 SERVER_ERROR`**, not the contractual
  `405 METHOD_NOT_ALLOWED`.
- **`Content-Type` is missing `charset=utf-8`** in practice.

HCAT's production client still has to cope with all four defensively
(mojibake decoding, treating IDs as opaque strings, not asserting on
Content-Type) regardless of what this mock update changes — see the
companion `2026-09-08_HCAT-integration-reference.md`.

## Recommended next real-server test

The single highest-value thing nobody has tried yet: call the real
server's `/patients` with `first_name=`, `father_name=`, `last_name=` as
**separate** query parameters (per v1.1) instead of a joined `q` string, and
see whether it's accepted, ignored, or rejected. Every existing data point
about patient search — from both evidence folders — used a single joined
string; none tested the structured shape v1.1 now specifies. Until that
test runs, treat the structured-field search as "per contract, not yet
independently verified" rather than "confirmed working."
